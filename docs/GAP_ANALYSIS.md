# Requirements Gap Analysis
Kerich Pharmaceuticals Smart Healthcare Hub — current build vs. BRD / FRS / NFRS / SAD / SRS

Generated by comparing the five uploaded requirement documents (the SRS
alone is 745 pages / 24,251 paragraphs) against the actual state of the
codebase built across this project so far.

**Scope reality check first**: the BRD's own project timeline (§13)
estimates **30–34 weeks with a full team** — developers, designers, QA,
BA, PM — to deliver this scope. What follows is not a todo list for one
session; it's an honest map of where things stand so we can sequence the
remaining work deliberately instead of guessing.

Legend: ✅ built · 🟡 partial · ❌ not built

## Not started at all (full subsystems)

- **Content Management System** — every page is hand-written HTML; there's no admin UI to edit page content, publish blog posts, or manage promotional banners without a code change.
- **Multi-branch / warehouse / supplier management** — the SRS gives this extensive treatment (170+ supplier mentions, a full warehouse chapter); current system assumes one location.
- **Wishlist, discount codes** — not built.
- **AI-assisted customer support (chatbot)** — not built.
- **Progressive Web App** — no manifest, no service worker, not installable.
- **Native mobile apps** — explicitly **out of scope for Phase 1** per the BRD (§4.5) — nothing to do here.

## Recommended sequencing

Given the scope, doing this in a sensible order matters more than doing
it fast. Roughly in priority order, reasoning included:

1. **Email/SMS notifications** — right now, orders, password resets, and
   delivery updates happen with *nothing* reaching the customer outside
   the app. This is the single gap most likely to actually hurt real
   users today, and it's comparatively contained (one service
   integration, then hooking it into events that already exist).
2. **Support ticketing (FR-021)** — customers currently have no way to
   raise a general issue; only healthcare consultations exist.
3. **CMS for the public site + a real Blog + Careers + Contact page** —
   turns the public-facing pages from hardcoded HTML into something
   marketing/content staff can actually maintain, and closes FR-001–005.
4. **Wishlist + discount codes** — comparatively small, high visible
   value for e-commerce.
5. **Google Analytics / Search Console / Tag Manager** — mostly
   configuration + a tracking snippet, low effort relative to value for
   an SEO-focused platform.
6. **PWA** (manifest + service worker + install prompt) — moderate
   effort, meaningful UX/retention value.
7. **Learning Management System** — this is genuinely its own product
   (courses, lessons, quizzes, certificates, progress tracking). Bigger
   than everything above combined.
8. **Multi-branch / warehouse / supplier management** — the SRS treats
   this as a major subsystem; only worth building once there's an actual
   second branch to manage.

Everything already built stays exactly as-is throughout — nothing here
requires touching working code, only adding to it.
